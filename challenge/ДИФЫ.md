# Чем отличаются две генерации `GET /api/days/{date}`

Промпт один и тот же. Правила разные: первая генерация шла по `challenge/rules-v1.md`, вторая — по `challenge/rules-v2.md`. Снимки кода лежат в `challenge/gen1/` и `challenge/gen2/`.

## Почему unified diff выглядит слабо

`gen1.diff` и `gen2.diff` посчитаны от одного и того же дерева `/tmp/wa-src-v1`, в котором чтения дня ещё не было. Оба патча поэтому похожи: тот же endpoint `GET /api/days/{date}`, те же DTO `DayResponse` и `DayEntry`, тот же ответ `400` с текстом «Неверная дата». Сдвиг — в том, какой тип приходит в роут и в каком файле вызывается `find`. В добавлении к пустой базе эти строки теряются среди одинаковых кусков. В `gen1-vs-gen2.diff` новый `Days.kt` и вовсе помечен как «Only in», без тела файла.

## Было и стало

| Место | Генерация 1 | Генерация 2 |
| --- | --- | --- |
| Где живёт чтение базы | В `Routes.kt`: `readDay` разбирает дату и дважды вызывает `store.find` — для `Log` и для `Schedule`. В `main` в `module` передаётся сам `store`. | В `activity/Days.kt`: `StoredDays.load` делает те же два `find`. Роут этого не видит. В `Application.kt` база оборачивается: `StoredDays(store)`, в `module` уходит `days`. |
| Как выглядит роут | `Route.api(sessions, store: ActivityStore)`. Ветка дня зовёт `readDay(store, date)`. | `Route.api(sessions, days: Days)`. Ветка дня зовёт `days.load(raw)`. |
| Где объявлен `BadDate` | Класс в `Routes.kt`. Обработчик `400` уже в `StatusPages` внутри `Module.kt`. | Класс стоит в `Module.kt`, сразу под `install(StatusPages)`, рядом с `ModelFailure`. Текст ответа тот же: «Неверная дата». |
| Как открывается H2 в тесте | `DayRoutesTest` сам вызывает `Database.connect` и передаёт JDBC URL и драйвер `org.h2.Driver`. | Тот же тест вызывает `connect(...)` из `app.work.server.activity`. Строка JDBC URL в тесте осталась: `connect` принимает её аргументом. |
| Сколько копий `idleTurns` | Две. Своя `private fun idleTurns()` в `DayRoutesTest.kt` и ещё одна в `RoutesTest.kt`. | Одна. `internal fun idleTurns()` в `RoutesTest.kt`. Тест дня берёт её оттуда и свою копию не объявляет. |
| Как записан беклог в фикстуре | `NewActivity("идея", ActivityKind.Backlog, null, day)` — с той же датой, что у журнала и плана. | `NewActivity("идея", ActivityKind.Backlog, null, null)` — `onDate = null`. |
| Как проверяется, что беклога нет в ответе | Отдельной проверки нет. Тест сверяет журнал со списком `ревью` и план со списком `созвон`. | Две явные проверки: summary `идея` нет ни в `body.log`, ни в `body.schedule`. |

## Роут

Фрагменты взяты из снимков как есть.

Генерация 1, `challenge/gen1/Routes.kt`:

```kotlin
fun Route.api(
    sessions: Turns,
    store: ActivityStore,
) {
    route("/api") {
        get("/days/{date}") {
            val date = call.parameters["date"].orEmpty()
            call.respond(readDay(store, date))
        }
```

Генерация 2, `challenge/gen2/Routes.kt`:

```kotlin
fun Route.api(sessions: Turns, days: Days) {
    route("/api") {
        get("/days/{date}") {
            val raw = call.parameters["date"].orEmpty()
            call.respond(days.load(raw))
        }
```

В первой генерации сразу под роутом лежат `readDay`, `pathDate` и `class BadDate`. Во второй этих функций в `Routes.kt` нет: разбор даты и два `find` живут в `StoredDays.load`.

## Что в правилах вызвало сдвиг

1. В v1 роуту было можно получить базу. Раздел «Паттерны»: «Роут только принимает тело и отвечает. Решение и база — за интерфейсом (`Turns`, `ActivityStore`, `ToolCatalog`, `LanguageModel`)». В конце файла прямо сказано: «Новый read-endpoint берёт данные из `ActivityStore`, не из модели». Первая генерация так и сделала: `store` в аргументах `api` и `readDay(store, date)`.

2. В v2 эта лазейка закрыта образцом, а не одним запретом. «Паттерны»: «Он не вызывает `ActivityStore` и не разбирает дату. Сообщения идут через `Turns`, чтение дня — через такой же узкий интерфейс с одним методом `load`». Ниже дан готовый вид ветки:

```kotlin
get("/days/{date}") {
    val raw = call.parameters["date"].orEmpty()
    call.respond(days.load(raw))
}
```

Вторая генерация повторила этот фрагмент. Рядом написано, что `Days.load` сам вызывает `ActivityStore.find` отдельно для `Log` и для `Schedule`.

3. Плохая дата привязана к `Module.kt`. В v2 в том же абзаце: «Пустое сообщение, чужая сессия, плохая дата и сбой модели — свои исключения рядом со `StatusPages` в `Module.kt`». И ещё раз в шаблоне: «Плохая дата — исключение из `Module.kt`, снаружи это `400` и `ErrorBody`». Поэтому `class BadDate` переехал из `Routes.kt` к обработчикам статуса.

4. Тест расписан по шагам. Последняя фраза v2: «Тест открывает базу через `connect()`, JDBC URL не копирует. `idleTurns` объявлен один раз. В фикстуре беклог записан с `onDate = null`, и тест проверяет, что его summary нет ни в журнале, ни в плане». В v1 на этом месте было только «Рядом тест на H2, как `ActivityStoreTest`» — отсюда прямой `Database.connect`, две копии `idleTurns` и беклог с датой дня.

## Что осталось похожим

Снаружи ответ тот же, и это уже было в первой генерации.

- DTO те же: `DayResponse` с полями `date`, `log`, `schedule` и `DayEntry` с полями `id`, `summary`, `jiraKey`, `createdAt`. Оба класса по-прежнему лежат рядом с роутом.
- Плохая дата по-прежнему даёт `400` и `ErrorBody("Неверная дата")`. Обработчик в `StatusPages` был уже в v1.
- Состав ответа тот же: журнал и план за день, беклог в тело не попадает, пустой день — пустые списки. Вторая генерация это не выдумала, она унаследовала.

Совпадение здесь ожидаемое: промпт не менялся, и v1 уже требовал журнал, план и `400`.
